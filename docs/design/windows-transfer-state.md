# Windows 传输状态文件访问失败修复

状态：2026-10-08，用户已授权实施与发布；基于拉取后的 `origin/main`（`d97a504`），已随 PR #39 合入，纳入 v2.4.0 离线包，仍待现场验收。

## 问题与范围

v2.3.0 现场下载在替换本机 `record.json` 时返回 `EPERM`，只确认了 3 MiB。之后 `resume` 返回相同失败快照，被误解为再次续传仍被锁住。现场持锁进程没有留下可核实证据，不指定锁的来源。

本轮只修改本机传输状态写入、后台故障反馈与操作指引。保留远端协议、目录保护、覆盖版本检查、提交对账、显式确认和双宿主接入行为。

## 已授权契约

- Windows 小型传输 JSON 状态文件仍通过写临时文件、同步、关闭句柄、原子替换落盘。仅对替换时的 `EPERM` / `EBUSY` 重试，最多五次；四次退避合计 375 ms，不包含系统调用自身耗时。其他错误和实际文件发布错误不按此规则重试。
- 重试耗尽时标记为可恢复的状态保存错误，保留 `code`、`syscall`、`path`、`dest`。这类错误的临时状态文件清理也受阻时，同时报告清理错误，不覆盖原改名原因。
- 独立驱动因状态保存受阻停止后，原记录与接收数据保留。记录本身不可改写时，将错误及一秒接回退避写到 `driver.json`；它仍仅用于诊断，执行权继续由 OS IPC 独占。无法写记录的错误先写诊断日志。
- MCP 观察结果 `paused` 是本机驱动暂停状态，底层传输记录保持最后持久进度。返回 `resumeRequired=true`、`acknowledgementRequired=false`，并带错误和 `retryAfter`。解除访问问题后按原编号恢复，继续重校验块与提交证据；不自动消费暂停结果。
- CLI `transfer wait` 在状态保存暂停时返回 `transfer-wait-paused`、退出码 1，不无限等待；`resumeAttempted=true` 只说明本次已派发新驱动，尚未开始的新驱动不会被旧暂停快照立即截断等待。
- 明确取消请求不等待数据续传的退避时间；接回取消流程后仍须核实停止与提交证据，不能把请求当作成功终态。
- `failed` 仍为终态，包括实际目标发布拒绝、其他 I/O 错误和旧 v2.3.0 失败记录。再次 `resume` 返回 `resumeAttempted=false`，明确只是已保存的失败结果，不复活旧终态。`unknown` 仍须人工核实且不能确认。
- 指引明确命令任务用 `remote_cancel(jobId)`，文件传输用对应上传/下载工具的 `action=cancel` 与 `transferId`；`ack` 不取消。未完成传输的 `sha256` 是预期摘要，不能作为接收文件已通过整文件校验的证据。
