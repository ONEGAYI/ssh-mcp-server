# 交互式支持与延后改动评估

2026-09-10。基于上游提交 `bd9d31962c72fbd1321225f85eb307cf33e53577` 的源码和官方依赖文档；未连接目标服务器或实施原型。复杂度为模块层面的工程判断，不是工期承诺。

## 结论

**首版保持非交互，预留任务执行方式的扩展位置。** 这符合用户已确认的 `make build`、大仓库 `rg` 搜索场景。交互式能力可以后加，前提是首版把任务身份、日志、完成回传和具体进程执行方式分开。

延后交互式不会免除其自身实现成本；能够避免的是重做文件工具、任务编号、状态查询、输出读取和完成通知。若将首版写成只在内存里保存 SSH stream 的一次性调用，后来补断线恢复和交互式就需要较大重构。

## 上游已有能力与缺口

- `src/models/types.ts` 和 `src/services/ssh-connection-manager.ts:1705`：已有 PTY 配置，exec 路径默认分配伪终端。PTY 是让程序以为自己连接着终端的操作系统设施，不等同于完整的 Agent 交互接口。
- `src/services/ssh-connection-manager.ts:1913`：shell transport 保存交互 SSH channel；该模式按连接串行排队执行命令。
- `src/tools/execute-command.ts`：工具只接受命令、工作目录、连接名和超时，并等待文本结果，没有运行中输入、关闭输入或调整终端尺寸的接口。
- 上游现有 channel 与内存状态不是本项目要求的可恢复任务存储。不能把已有 `pty: true` 宣称为已支持断线可恢复的交互式任务。

## 按交互程度评估

| 能力层次 | 例子 | 新增工作 | 延后改动量判断 |
|---|---|---|---|
| 非交互命令 | make build、rg 搜索 | 可恢复任务、日志、退出结果、取消、完成回传；首版输入关闭 | 首版本身需解决的核心工作，不能以“非交互”视为简单包装 |
| 管道式输入 | 给运行中脚本发送一行文字 | 输入通道、发送与关闭输入接口、读写并发、背压与退出竞争 | 中等；主要增加输入路径。断线后输入恢复还需远端持有该通道 |
| 终端式交互 | 需要终端的 REPL、交互调试器 | PTY 生命周期、控制字符、终端尺寸、原始输出；必要时提供屏幕快照 | 较大；主要增加终端执行器与输出解释，基础任务管理可复用 |
| 可重连的终端会话 | 掉线后继续同一调试器或终端界面 | 远端持续持有 PTY、重新附着、输入控制权、重复输入处理、终端状态恢复 | 大；需要独立的远端会话管理与离线兼容验证 |

管道式输入通常不等于终端交互；具体工具是否需要 PTY 必须按其行为验证。像 Vim 一类全屏界面还涉及光标、重绘与屏幕状态，不能仅把历史文本日志拼接后当作当前屏幕。

## 首版建议预留的边界（尚非最终接口）

1. **任务与连接分开**：持久任务编号和记录独立于 SSH channel；连接中断不直接标记任务失败，恢复时核对实际状态。
2. **等待与执行分开**：单次查询或本机等待结束不杀远端任务；取消是显式操作。任务执行上限与等待时限分别表达。
3. **执行器可扩展**：让负责启动和控制进程的模块采用窄接口；首版仅实现非交互方式，未来可增加终端方式。不要提前暴露不可用的交互工具。
4. **输出可增量读取**：以稳定偏移读取日志，保留原始字节与必要的流信息，展示层再解码或裁剪；未来 PTY 的合并输出也能表达。日志保留策略与工具返回大小分别控制。
5. **输入能力显式区分**：首版任务声明不支持输入并关闭标准输入；未来新增输入/EOF 接口，不改变原有启动、查询和等待行为。不靠分析提示符猜测是否可输入。
6. **远端保存控制信息**：为进程控制、状态恢复与完成记录留下明确入口。首版非交互任务不依赖持续保持的 SSH channel；将来保活 PTY 可作为新的远端执行方式。

首版选择默认无 PTY、显式工作目录和环境变量是建议，不能默默改变上游旧工具默认行为；兼容策略需在实施设计中明确。Shell 管道、重定向和多条命令不属于交互式功能，可以保留。

## 推荐实施顺序

- 首先验证非交互任务在 SSH 断开、本机等待退出后继续，以及重连取得原任务日志和退出结果。
- 同时验证 ZCode 原生后台 Shell 的完成回传，以及客户端重启后重新登记等待和补发；这是当前核心需求，不因延期交互式而推后。
- 再完成大输出分段、取消、并行任务和文件保护。`rg` 无匹配的退出码应原样返回，不与传输失败混淆。
- 将来有实际交互需求时，先实现管道式输入；需要真实终端并且必须断线存活时，再引入可重连的 PTY 执行器。

候选的终端持有方式包括目标机已有的 tmux 或自行离线部署的辅助程序；目前没有确认远端已安装 tmux，也未选定它作为依赖。仅重新建立 SSH 连接不应被当作恢复旧终端的实现方案。

## 证据与待验证项

- [ssh2 Channel 文档](https://github.com/mscdex/ssh2#channel)：channel 是双向流，支持输入、终端尺寸和信号等底层操作；部分服务端可能忽略信号请求。底层 API 存在不代表上游 MCP 已暴露或可靠管理这些能力。
- [tmux 官方入门](https://github.com/tmux/tmux/wiki/Getting-Started)：支持脱离后再附着原有终端会话，为可重连 PTY 提供一种实现参照。
- 目标 CentOS 7 的实际命令、运行时、进程退出策略、文件系统和权限均未探测；尚不能给出可信的人天估算。
