## 可行性判断与限制

**候选运行方式**：本机运行现代 Node.js MCP 服务，通过 SSH 使用远端已有命令或辅助脚本。这样无需在 CentOS 7 上运行现代 Agent 客户端；实际可用的 SSH 通道、SFTP、Shell 与运行时仍需探测。

**写入保护候选**：读取时记录文件版本，写入时校验预期版本，冲突则拒绝。仅比较修改时间不够稳妥；内容摘要也只能判断所比较的内容是否相同，无法独立证明文件中途从未变动。还需讨论读取范围、会话隔离和写入者类型。

**并发边界**：校验后再写入仍存在两步之间被其他进程修改的窗口。临时文件加原子替换可避免半写文件，但不自动提供跨任意外部写入者的“比较并替换”保证。协作锁只能约束遵守同一锁规则的写入者。

**已确认的命令边界**：用户明确不需要约束所有 Shell 写入，接受通过提示词引导 Agent 优先使用 MCP 内置文件工具。普通命令可以产生文件副作用，文件工具保护不表述为全系统写入防护。

**后台任务方向**：用户已确认非交互任务不阻塞主 Agent，完成后触发后续处理；SSH 断线或客户端退出时远端任务继续，重连后恢复跟进。拟提供独立任务编号、远端日志和结束记录，以及启动、查询、增量输出、等待与取消操作。网络中断后不能盲目重发有副作用的启动命令，启动去重与状态核对是实施设计中的必需项。

**完成提醒边界**：[MCP 2025-11-25 Tasks 规范](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/tasks)定义延后取结果、轮询和可选状态通知，且该版本将 Tasks 标为实验特性。协议允许通知，不代表客户端会唤醒模型并继续任务。ZCode / Codex 的具体支持尚未核实，不能提前承诺。

## 第一轮访谈

1. **已确认**：首要验收对象为内网 Win11 上的 ZCode，开发环境在经 SSH 访问的 CentOS 7；典型命令见第 6 项。
2. **已确认**：Linux 离线、没有 root 权限，需照顾旧版 glibc；用户表示其他方面应该没有限制。可考虑用户目录离线部署，运行时选择仍待探测。
3. **已确认**：任务后台执行或不阻塞，结束后主动找 Agent 并触发下一步。仅返回编号、依赖 Agent 主动查询不满足要求。
4. **已确认**：接受 MCP 内置文件工具的保护范围；通过提示词引导优先使用，不做任意 Shell 写入拦截。
5. **已确认**：远端继续，重连后恢复跟进。服务器自身重启后的自动重跑不纳入本轮推荐范围。
6. **已确认**：`make build`、`rg` 搜索大仓库等非交互命令；首版不需要交互式输入。用户要求评估交互式实现难度与延期代价，见[专题评估](interactive-assessment.md)。

第一轮方向性问题均已回答。文件版本检查细节、任务与原始对话的恢复接入、远端运行时探测等仍需形成具体设计与验证，不能把方向确认等同于全部实施契约已确认。

## ZCode 完成回传机制调查

2026-09-10 查询官方文档，以下描述不代表用户安装版本已经实测通过。

- [Subagents](https://zcode.z.ai/en/docs/subagents)：后台子代理不阻塞主任务，主回合可以结束；子代理结果会自动回到主对话，Agent 随后继续处理。默认权限的子代理可以使用已连接的 MCP 工具。
- [ADE Tools](https://zcode.z.ai/en/docs/ADE-tools)：终端命令支持后台执行，主回合不等待。这一页未单独明确所有后台命令完成都会唤醒模型，不能据此直接作出同等承诺。
- [Hooks](https://zcode.z.ai/en/docs/hooks)：异步 command hook 的后台输出不能注入上下文；Stop hook 只在模型准备结束时介入，连续续跑最多三次。单靠这两种 hook 不足以承诺任意时刻的任务完成唤醒。
- [MCP 配置](https://zcode.z.ai/en/docs/mcp-services)：支持接入 MCP 服务，但已查页面未明确承诺 MCP 任务状态通知会唤醒主 Agent。

**用户确认的接入方向**：用户补充 ZCode 原生后台 Shell 也能在结束时回传并触发 Agent，并明确其比额外运行子代理务实。因此优先采用原生后台 Shell 启动本机等待程序，远端任务结束后由程序退出并返回结果。该行为的依据是用户说明，目标版本尚未实测；后台子代理不作为首选。

**接入细节待设计**：文件操作和远端任务能力由 MCP 核心提供；本机等待程序如何访问同一任务记录、复用配置和关联原始对话尚未定案。必须将“ZCode 工具调用以后台方式执行”与“Shell 文本中自行加 &”区别开：后者不能单独保证被 ZCode 作为后台任务管理。还需防止远端任务已启动但本机等待未登记的遗漏窗口。

**可靠性需求的候选分解**：程序保存任务编号、所属工程/对话、命令、日志位置和未确认的完成事件；程序通过 SSH 等待或轮询远端状态，不依赖模型反复思考。客户端负责将结果送回所属对话。用户已要求客户端重启后恢复跟进，但重复投递、确认时机、重新登记 ZCode 后台等待和已关闭对话的具体接入方式仍待验证。

远端离线不要求 Linux 主动访问互联网或连接 Win11；由 Win11 发起的 SSH 通道可以承担状态获取。网络断开时无法即时送达；恢复后的补发已纳入用户要求，具体接入待验证。

## 已确认的写保护范围

| 场景 | 建议行为 |
|---|---|
| Edit / Patch 修改已有源码 | 必须有先前读取记录；写入时比较预期文件版本，不匹配就拒绝并要求重读 |
| Write / Upload 覆盖已有文件 | 与 Edit 共用保护，避免换一个工具就直接覆盖 |
| 创建新文件 | 仅在目标不存在时创建；如果目标已存在，转为覆盖规则 |
| 删除或移动已有文件 | 校验对象身份与预期版本；目标覆盖也受保护。目录递归操作另行定义 |
| 编译、测试、仿真产生文件 | 不要求每个输出文件先读；属于命令产生的副作用 |
| Shell 重定向、sed、Python 等修改源码 | 通用命令可绕过专用文件工具。可通过规则要求源码编辑使用受保护工具，但不能把规则写成强制安全隔离 |

用户接受以上开发防误覆盖范围，明确无需把任意命令限制得更严。通过工具描述、提示词或技能指引优先使用受保护文件工具，不引入全面 Shell 写入拦截。具体文件版本与并发契约另行确定。
