# 大文件读写采用元数据检查与唯一原文匹配

## 状态

2026-09-12 用户在逐点设计访谈中确认。决策已接受，尚未实施；当前代码仍采用全文摘要与 16 MiB 限制。

## 背景

目标场景包含约 200 MB 网表的局部读取和参数修改。当前文件工具在远端加载全文并计算版本，限制了大文件处理；下载每个分块还会重复生成全文快照。

文件在 CentOS 7 服务器上扫描，与把全文下载给本机 Agent 是两件事。减少全文哈希主要降低远端扫描成本；避免全文驻留内存还需要分块处理，不能仅删除哈希计算。

## 决定

- 取消文件工具每次读写时以全文内容哈希校验版本的要求，改用文件身份、大小、修改时间和状态变更时间等元数据检查。读取前后及修改提交前检查变化；具体字段编码与旧凭据迁移方案留待实施规格确定。
- 移除 16 MiB 文件体积门槛，不另设统一文件体积上限。读取与搜索受返回量、执行预算约束；写入与传输还受已确认的空间额度和实际磁盘可用空间约束。必须采用有界处理，不能把“没有固定体积上限”实现为无限内存分配、无限输出或无限执行。
- 保留服务签发的 readToken、会话与路径归属、实际已读字节区间、截断保护和协作锁。元数据检查本身不授予已读资格。
- replace 继续要求 oldText 在整个目标文件中恰好匹配一次，并在修改时校验匹配原文。没有匹配时拒绝并提示重读；多处匹配时拒绝，要求 Agent 读取更多上下文并扩大 oldText，直到唯一。
- 扩大后的完整匹配片段也必须被已读区间覆盖。newText 保留不需要修改的上下文；不自动替换第一处、不隐式替换全部匹配，也不以模糊匹配消除歧义。
- 元数据变化或原文不符时拒绝本次修改，要求重读；不把旧读取范围自动转授给已变化的文件。

## 影响与保证边界

- 局部读取不再为版本摘要额外扫描全文。按行定位、编码检查等是否仍需扫描，取决于后续实现；本决策不承诺所有局部读取都能直接随机定位。
- 全文唯一匹配仍需在远端排除其他匹配，可以流式扫描；临时文件替换仍可能复制整个文件。这些操作不要求通过网络传输全文。
- 接受不再以全文摘要兜底：内容变化若未反映在检查的元数据中，且不影响核对的原文，可能漏检。对不遵守协作锁的外部进程，仍不承诺消除检查与提交之间的竞争，也不证明文件历史上从未改变后恢复。
- 本决策不取消传输或离线交付包的完整性校验。后续已确认的整体覆盖规则见 [ADR 0008](0008-explicit-version-bound-overwrite.md)，文件管理工具去留见 [ADR 0007](0007-file-management-through-shell.md)，搜索后端与忽略规则见 contracts.md；完整传输采用分块校验及最终 SHA-256 核对，见 [ADR 0009](0009-resumable-file-transfers.md)。
